## 3. Open thread: LLM "0 output" bug — root caused, mostly fixed

User saw 0 output tokens / empty replies when chatting through `https://ai.songsongcard.shop/v1`.
Root cause: that proxy ignores `stream:false` and always replies in SSE format (`data:` lines + `[DONE]`).
Our client was parsing the response as plain JSON and only saw the empty metadata frame.

Fix (committed in `9c13993`): client.rs now ALWAYS sends `stream:true` and the parser handles SSE
(accumulating `delta.content` across chunks) AND plain JSON. The user's `gpt-5.4` test prompt returned
"hello" correctly via curl after this change.

Lesson saved as feedback memory: don't dismiss a user hypothesis with shallow code reading; probe runtime first.

## 4. Tomorrow's main task — Topic Survey v2 (user-approved framework, revised)

Current 主题发现 returns flat S2 results. The user wants a structured literature survey,
but **directly asking the LLM to emit the paper list is wrong** — DOIs / PI names / years
hallucinate. The correct architecture is **two-phase: LLM provides the structural skeleton
+ search plan, then S2 grounds it with real papers**. The LLM never invents papers; it only
plans queries and (optionally) annotates the retrieved ones.

### Architecture

```
[topic input: "极端超短脉冲激光"]
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 1 — LLM SURVEY SKELETON (1 call, structured JSON) │
│                                                          │
│  output = {                                              │
│    subareas: [                                           │
│      { name, year_range,                                 │
│        summary,                ← LLM-written narrative   │
│        search_terms: [...],    ← 2-4 English terms       │
│        pi_hints: [...],        ← optional PI names       │
│      },                                                  │
│      ...                                                 │
│    ],                                                    │
│    key_pis: [{name, why_central}],   ← for PI map        │
│  }                                                       │
│                                                          │
│  ⚠️  This step does NOT emit titles/DOIs/papers. The      │
│      LLM only describes the field structure + tells us   │
│      what to search for.                                 │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 2 — S2 GROUNDED RETRIEVAL (N parallel calls)      │
│                                                          │
│  for each subarea:                                       │
│    for each search_term in subarea.search_terms:         │
│      bulk_by_citations(term, year_filter=subarea.range)  │
│    for each pi in subarea.pi_hints (if any):             │
│      search_semantic_scholar("by " + pi)                 │
│                                                          │
│  Then per-subarea: dedupe by paper_id, rank by citation, │
│  take top K (e.g. 5-8). All papers are REAL.             │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 3 (optional, 1 more LLM call) — ANNOTATE          │
│                                                          │
│  Pass back the LLM the [subarea, [paper title+abstract]] │
│  pairs and ask it to:                                    │
│    - write why_important per paper (1-2 sentences 中文)  │
│    - flag 8-12 must_read across all subareas             │
│                                                          │
│  Skip this if cost matters — UI can fall back to         │
│  showing title + abstract + citation count alone.        │
└─────────────────────────────────────────────────────────┘
        │
        ▼
    TopicSurvey {
      subareas: [{ name, summary, papers: [SurveyPaper{...}] }],
      key_pis: [{name, why_central}],
      must_read_ids: [...],
      // every paper carries a REAL doi/title/year/authors/citation_count from S2
    }
```

### Why this beats "LLM emits papers directly"

- **No hallucinated DOIs** — every paper is one S2 returned for a real query
- **Real citation counts** — used for ranking + visible to the user
- **Authors come from S2** — PI name doesn't have to be guessed (though Phase 1's `pi_hints` is useful for the dedicated PI search)
- **LLM still does the hard part** — domain decomposition into subareas with year ranges and search vocabulary; this is exactly what LLMs are good at
- **Cost-bounded** — Phase 1 + Phase 2 ≈ 1 LLM call total in the cheap version; Phase 3 adds one more call if annotation is desired
- **Recovers when S2 doesn't have a "classic"** — if Phase 1 says foundational paper is from 1992 and S2 returns nothing, the subarea still has its narrative + the more recent papers; we show a "未找到 1992 奠基文献,可能需要手动补" hint rather than fabricating

2. **`src-tauri/src/ingest/topic_survey_retrieval.rs`** (new module)
   ```rust
   pub struct GroundedSubarea {
     pub spec: SubareaSpec,           // pass-through from Phase 1
     pub papers: Vec<SearchResult>,   // real S2 hits
   }

   pub async fn ground_survey(
     client: &reqwest::Client,
     skeleton: &SurveySkeleton,
     per_subarea_topk: usize,         // e.g. 6
   ) -> Result<Vec<GroundedSubarea>>
   ```
   - For each subarea: fan out 2-4 `bulk_by_citations` calls (one per search_term)
     plus N `search_semantic_scholar` calls for each pi_hint
   - Merge per subarea: dedupe by paper_id, rank by citation_count, take top K
   - **Cross-subarea dedupe**: a paper might match multiple subareas. Assign to
     the subarea whose search term had the highest matching score (or just
     "first wins" for MVP). Don't show the same paper twice.

3. **`src-tauri/src/ai/topic_survey.rs::annotate_survey(client, profile, grounded)`** (Phase 3, optional)
   ```rust

     pub paper_notes: HashMap<String, String>,  // paper_id → why_important (中文)
     pub must_read_ids: Vec<String>,
   }

   pub async fn annotate_survey(...) -> Result<SurveyAnnotation>
   ```
   - Builds a compact prompt: for each subarea, list [title, year, abstract_first_200_chars]
   - LLM returns JSON with per-paper Chinese annotation + must_read flags
   - If this call fails / times out, we still ship the survey without annotation

4. **`commands::topic_survey(topic, annotate: Option<bool>)`** — orchestrates
   plan_survey → ground_survey → optionally annotate_survey, returns the

5. (Phase 2 work, post-MVP) `commands::verify_doi_batch` — light-weight DOI

### 4.1 System prompt for Phase 1 (rewritten — emits NO papers)

```
You are a domain expert helping a PhD student plan a literature survey.
The user gave you a (possibly Chinese) research topic.

You will NOT list any specific papers — another tool will fetch real papers
from Semantic Scholar based on the plan you produce. Your job is to:

1. Decompose the field into 4-7 subareas, ordered historically OR by
   technique (you decide which makes more sense for this topic).
2. For each subarea write a one-paragraph narrative summary (in 中文)
   explaining what this subarea contributed and why it matters.
3. For each subarea provide 2-4 English search terms that an academic
   search engine would use to surface the right papers. Be specific —
   "ultrafast laser" is too broad; prefer "high-harmonic generation",
   "carrier-envelope phase", etc. These terms will be passed verbatim
   to Semantic Scholar.
4. Optionally name 1-3 PI / senior authors per subarea (in pi_hints) —
   we'll search S2 for their work in addition to the topic terms.
5. List 5-10 key_pis across the whole field with a one-line note on
   why each one is central.

Output ONLY a JSON object — no markdown fence, no prose:

{
  "subareas": [
    {
      "name": "<English subarea name>",
      "year_range": [<start_int>, <end_int>],
      "summary": "<one paragraph in 中文>",
      "search_terms": ["<English term>", ...],
      "pi_hints": ["<full name>", ...]
    },
    ...
  ],
  "key_pis": [
    {"name": "<full name>", "why_central": "<one-line in 中文>"}
  ]
}

Rules:
- 中文 in summary / why_central; English in search_terms; PI names native.
- Resist over-broad search terms — each term should return 20-200 papers,
  not 20,000.
- Don't invent terms. Use vocabulary actually used in titles/abstracts.
- year_range is inclusive; pick the era the subarea was most active.
```

### 4.2 System prompt for Phase 3 (annotation)

```
You will annotate a list of papers that were retrieved from Semantic Scholar
based on a topic survey plan you helped produce. For each paper, write:
- why_important: 1-2 sentences in 中文, specific to what this paper proved/built
- must_read: true if this is foundational or essential for the field

Across all papers, mark exactly 8-12 as must_read=true. Choose for breadth
(don't pile all must_reads into one subarea).

Input format (you'll receive):
[
  {"subarea": "<name>", "papers": [
    {"id": "<s2 id>", "title": "...", "year": ..., "abstract": "..."}
  ]}
]

Output ONLY a JSON object:
{
  "annotations": {
    "<paper_id>": {"why_important": "...", "must_read": true|false}
  }
}

Rules:
- Use the abstract to be specific. "提出了 X 方法" beats "讨论了 X".
- If the abstract is missing/empty, still write one sentence about what
  the title suggests.
- must_read=true for ~30-40% of papers; not all of them.
```

## 6. Architecture notes / gotchas from today's work

- **sqlx Option binding pitfall**: `bind(Option::<&str>::None)` on a nullable column did NOT translate to SQL NULL on SQLite — it stored an empty string or the previous value (we hit this on `highlights.note`). Fix: split into two queries (`SET col = ?` vs `SET col = NULL`). When reading nullable columns, use `try_get::<Option<String>, _>("col").unwrap_or(None)`, NOT `try_get("col").ok()`. Watch for this in `storage/papers.rs` — same pattern exists there but isn't triggering because we never clear those columns.
- **react-pdf-highlighter pdfjs version lock**: RPH bundles a specific pdfjs-dist (currently 4.4.168). If you install standalone pdfjs-dist at a different major, the worker / API version mismatch causes silent black-pane failure. Always pin pdfjs-dist to match `node_modules/react-pdf-highlighter/node_modules/pdfjs-dist/package.json`.
- **Tauri asset:// flaky on this host**: `convertFileSrc()` + `app.security.assetProtocol.enable` SHOULD give pdfjs a fetchable URL for local PDFs, but in our setup the fetch hangs silently. We bypassed with `paper_read_pdf_bytes` (Vec<u8> via IPC → Blob URL in JS). Slower for large PDFs but deterministic. Revisit asset:// if/when Tauri stabilizes it.
- **xdg-open is slow on Arch+Zen**: takes 5-10s doing DE detection before launching the system PDF viewer. `paper_open_pdf` spawns it detached so the user gets the eventual window without blocking Tauri.
- **Chinese-gateway proxies force SSE**: songsongcard.shop (new-api fork) ignores `stream:false`. Always send `stream:true` in chat_complete; the parser handles both shapes.
