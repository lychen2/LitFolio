# NeuInk Reading Workflows Audit for Mono Integration

## Audit Basis

- NeuInk source: fixed checkout `/tmp/litfolio-neuink-audit` at commit `11b848e0cfe9100a0386bcf2d4f3b839148d3b99`.
- LitFolio source: current workspace implementation, with the Mono parent and child designs treated as the target contracts.
- Method: static source audit of end-user reading paths and persistence boundaries. This audit did not execute NeuInk, so visual polish and runtime performance claims are limited to behavior represented in source and tests.
- Citation prefixes: `N:` is the fixed NeuInk checkout, `L:` is the LitFolio workspace, and `M:` is the Mono task/spec tree.

## Decision Summary

NeuInk is most valuable as a **workflow and domain-contract donor**, not as a module that can be placed wholesale behind a Mono plugin boundary.

The highest-value contract is a durable provenance chain:

```text
accepted document revision
  -> stable source segment
  -> PDF/reflow navigation target
  -> note source link + immutable snapshot
  -> indexed backlink
  -> annotation/export citation
```

The parser that proposes segments can be a `document-services` plugin. Once a result is accepted, the normalized document revision, segment identities, note links, snapshots, backlinks, and annotations must be core-owned. Otherwise disabling or excluding the parser plugin would break core notes and exports, violating Mono's requirement that core local document behavior remain complete when document integrations are absent. Mono already assigns PDF files, extracted Markdown, notes, annotations, and core export jobs to core storage, while plugin data belongs in isolated sidecars (`M:.trellis/tasks/07-23-litfolio-mono/design.md:44-64`; `M:.trellis/tasks/07-23-mono-plugin-integrations/design.md:35-44`).

NeuInk's implementation also exposes contracts that should **not** be copied unchanged: backlinks are rebuilt by reading every note in the frontend, ordinary note/source-link persistence spans separate writes without a revision contract, open tabs are not restored, and global native context menus are suppressed. Mono should retain the user-facing workflows while replacing these persistence and host behaviors.

## Required Mono Contract Changes

1. **Extend core document ownership.** Add accepted `DocumentRevision`, `DocumentSegment`, and `SegmentAnchor` value types. The document plugin can create a staged proposal; only a core "accept revision" command changes canonical document Markdown/segments. The accepted result remains readable after plugin disable.
2. **Extend Reader host surfaces.** Existing slots are sufficient for actions and side panels, but not reflow or arbitrary split content. Add fixed, typed `reader.contentModes` and `app.workspaceSurfaces` slots, with core-owned built-ins, capability checks, failure isolation, and lifecycle disposal.
3. **Add core provenance APIs.** Required methods include create/remove/resolve source link, query backlinks by segment, query links by note, refresh/remap against a new document revision, and render/materialize for export. Plugins receive DTOs and opaque asset handles, never the core pool or raw paths.
4. **Unify dirty/save lifecycle.** A surface must expose `status`, `save`, `discard`, and `flush` through the app host. App shutdown, tab close, workspace switch, plugin disable, and paper change invoke the same protocol and retain the surface when save fails.
5. **Revise annotation contract only after mapping is approved.** The first Mono annotation child should land unchanged except for an optional future-proof source-anchor field if feasible. A later contract revision decides whether segment-only annotations become `SourceComment` or source-linked notes.

## Migration and Compatibility Rules

- Never move accepted segment/provenance records into `<library-root>/plugins/<id>/data.db`; plugin removal must not orphan note meaning.
- Keep existing highlight geometry and planned `pdf_notes` conversion authoritative. Segment anchors are nullable enrichment, not a replacement for PDF coordinates.
- Preserve existing `note.md` and `paper_note_sections` content byte-for-byte until a user-visible conversion is explicitly accepted. Assign deterministic owner IDs externally rather than rewriting note text just to insert IDs.
- Reparse must create a new document revision, attempt deterministic segment remapping, retain old snapshots, and produce counts for unchanged/moved/changed/unresolved links and annotations. Never rewrite all links silently.
- Legacy/import conversion must be previewable, idempotent, backed up, and export unmappable NeuInk records rather than discarding dynamic kinds or stale source references.

## NeuInk Behaviors to Reject or Replace

- **Reject frontend library-wide backlink reconstruction.** It loads notes in batches and silently ignores failures; use a core reverse index and explicit stale/unresolved state (`N:apps/desktop/src/modules/reader/components/useSourceBacklinks.ts:31-51`, `N:apps/desktop/src/modules/reader/components/useSourceBacklinks.ts:66-81`).
- **Reject raw dynamic annotation kinds as the core discriminator.** Keep a typed union and validate extension metadata separately (`N:crates/neuink-domain/src/annotation.rs:7-18`).
- **Replace multi-file best-effort source-link saves with one transactional/journaled command.** NeuInk snapshots correctly but writes note content, note metadata, and link sidecars independently (`N:crates/neuink-workspace/src/note.rs:55-97`, `N:crates/neuink-workspace/src/note.rs:172-178`).
- **Reject global context-menu suppression.** Menus must be scoped to registered Reader targets and preserve platform editing/accessibility actions (`N:apps/desktop/src/app/App.tsx:598-619`).
- **Do not treat recent-reading IDs as session recovery.** Restore a versioned surface layout and draft journal, validating every paper/note/plugin owner before opening (`N:apps/desktop/src/app/App.tsx:546-555`; `N:apps/desktop/src/app/workspaceSurface.ts:25-31`).

## Recommended Delivery Order

1. Land Mono core boundaries and the planned revision-safe PDF annotation controller.
2. Add accepted document revisions/segments and the core provenance link/backlink schema, with parser-plugin acceptance boundaries.
3. Add source-aware note anchors, snapshot rendering, atomic/journaled save, export materialization, and migration fixtures.
4. Add generic reflow plus typed workspace surfaces and synchronized PDF/reflow navigation.
5. Add context-command contributions, session restore, and optional richer editor/export features after core-only and plugin-disabled E2E tests prove links and notes remain usable.

## Minimum Acceptance Tests for Integration

- Core-only: open PDF, existing highlights/text notes, plain note editing, basic Markdown export, and source snapshots from previously accepted segments work with `document-services` absent.
- Reparse: unchanged links resolve live; changed/missing links show snapshot and status; remap report is deterministic and rollback-safe.
- Save/recovery: rapid annotation/note edits cannot stale-overwrite; failed save keeps the surface open; forced process restart offers the latest journaled draft; note/link mutation is all-or-nothing after recovery.
- Workspace: PDF/reflow/note surfaces move between panes, restore after restart, reject missing owners safely, and flush or block on close.
- Plugin lifecycle: enabling/disabling parser, export, or context-action contributions changes only their UI/jobs; accepted documents, user notes, source links, backlinks, annotations, and baseline exports remain intact.
