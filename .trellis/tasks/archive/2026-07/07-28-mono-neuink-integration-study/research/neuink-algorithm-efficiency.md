## 2. Document segment normalization and remapping

| Decision | Concrete algorithm/pattern | Source evidence | Asymptotic or I/O benefit | LitFolio owner | Benchmark threshold |
| --- | --- | --- | --- | --- | --- |
| **Adapt** | Normalize provider variants in one streaming pass. Canonicalize type/page/bbox/text/role, compute a content fingerprint, and append a duplicate occurrence ordinal. Validate ordering, page bounds, geometry, assets, and size while building the staged candidate; activate only after validation. | NeuInk normalizes multiple response shapes and derives IDs from type, page, geometry, text, role, and duplicate ordinal at `N:crates/neuink-parser/src/normalizer.rs:9-58`; canonical schema versioning is at `N:crates/neuink-domain/src/parser.rs:5-17`. Provider-specific fields leak into `SourceSegment` at `N:crates/neuink-domain/src/segment.rs:7-28` and must not enter the core contract. | One pass with a hash map is `O(S)` expected time and `O(U)` memory for `S` segments / `U` distinct fingerprints. Combined normalization and validation avoids a second parse of raw artifacts and prevents invalid candidates from causing canonical FTS writes. | `document-services` owns transport and raw normalization. Core document service owns candidate validation, `DocumentRevision`/`DocumentSegment`, atomic activation, and FTS projection. | Normalize and validate 10,000 mixed segments, including 10% duplicate fingerprints, in `<= 200 ms` and `<= 2x` canonical payload peak memory on the reference desktop fixture. |
| **Adapt, do not reuse as identity** | Remap old to new revisions in two bounded stages: exact fingerprint bucket match first; then score only candidates in the same/adjacent page and semantic-kind buckets using quote hash/text similarity plus bbox distance. Resolve only a unique score above threshold; otherwise retain the immutable snapshot as unresolved. Segment fingerprints are revision-local, never annotation identity. | NeuInk's fingerprint changes when parser text/geometry changes (`N:crates/neuink-parser/src/normalizer.rs:31-57`). Page/kind buckets keep fuzzy candidate work near `O(S * B)` for bounded bucket size `B`, avoiding all-pairs `O(S_old * S_new)`. Only changed links require persistence. | Core provenance/remap service. Parser plugins may supply staged revisions but cannot rewrite links or annotations. | For 10,000-segment revisions with 90% unchanged, 8% moved/edited, and 2% removed, deterministic remap must finish in `<= 500 ms`, with `100%` exact recovery of unchanged segments and zero false automatic matches in the ambiguity fixture. |

## 3. Atomic persistence

| Decision | Concrete algorithm/pattern | Source evidence | Asymptotic or I/O benefit | LitFolio owner | Benchmark threshold |
| --- | --- | --- | --- | --- | --- |
| **Adopt with platform hardening** | For one file artifact: serialize completely, write a unique sibling temp file, flush and `sync_all`, atomically replace destination, then sync the parent directory where required. Preserve/restore a backup only on platforms whose replace primitive needs it. | NeuInk implements temp write, file sync, rename, and replacement fallback at `N:crates/neuink-workspace/src/atomic_write.rs:12-69`. Current LitFolio notes overwrite directly at `L:src-tauri/src/storage/notes.rs:23-32`. | Still `O(B)` bytes for payload size `B`, but readers observe old or new content, never partial bytes. | **Reject and replace** | Reject independent atomic writes for a logical multi-resource mutation. Use one SQLite transaction when all canonical rows fit SQLite; otherwise use a durable stage journal: prepare files, fsync stage, commit DB pointer/receipt once, promote idempotently, and recover or roll back on restart. | NeuInk writes note Markdown and metadata/source-link sidecars separately at `N:crates/neuink-workspace/src/note.rs:55-97,131-178`; note creation also spans independent replacements at `N:crates/neuink-workspace/src/workspace.rs:164-191`. LitFolio already uses SQL transactions for relational bulk changes, e.g. `L:src-tauri/src/storage/dedup/merge.rs:8`. | A DB transaction turns `K` independently visible writes into one visibility boundary and normally one WAL commit. The journal keeps cross-filesystem work `O(total bytes + K)` while eliminating partial canonical state and repeated full backup copies on retry. | Core proposal/provenance/document storage. Plugins can stage candidates but cannot commit `library.db`, core FTS, or canonical files. | A failure-injection suite covering every boundary of a 100-link note/revision mutation must produce `100%` all-old or all-new externally visible state after restart, and a second recovery run must perform zero additional logical mutations. |

## 4. Job and cancellation efficiency

| Decision | Concrete algorithm/pattern | Source evidence | Asymptotic or I/O benefit | LitFolio owner | Benchmark threshold |
| --- | --- | --- | --- | --- | --- |
| **Reject and replace** | Reject status-only cancellation. Register one real cancellation token per `(owner, job_id, plugin_generation)`, pass it through network polling, parsing, indexing, tools, and commit guards, and select/check it at every bounded safe point. Revoke generation before disable drain; a cancelled generation cannot publish success. | NeuInk cancellation only relabels an in-memory job at `N:crates/neuink-job/src/lib.rs:167-187`; custom parser polling can sleep for up to 900 attempts without a token at `N:crates/neuink-parser/src/custom_endpoint.rs:430-457`. LitFolio has a working token pattern for batch work at `L:src-tauri/src/commands/batch.rs:13-28,83-92`, while generic `JobRepo::cancel` currently changes only persisted status at `L:src-tauri/src/storage/jobs.rs:148-155`. | Token cancellation is `O(1)` signal propagation. It avoids up to the remaining poll timeout/network work and prevents late-result writes. Owner/generation indexing makes plugin disable cancellation `O(J_owner)` rather than scanning unrelated jobs. | Core host job runtime; each core/plugin operation must cooperate through the injected token. | For a 100-job mixed workload, p99 time from cancel request to task stop must be `<= 250 ms` excluding non-interruptible OS calls, and the test must observe zero success events or canonical writes after cancellation acknowledgment. |
| **Adapt** | Keep a bounded in-memory active-job/event map for `O(1)` dispatch, but persist lifecycle truth in SQLite. Coalesce progress to the latest value per job and flush on a fixed interval or meaningful percentage change; terminal transitions flush immediately and carry monotonic event sequence numbers. | NeuInk uses an in-memory `HashMap`/bounded `Vec` at `N:crates/neuink-job/src/lib.rs:189-284` and a frontend event subscription at `N:apps/desktop/src/shared/hooks/useWorkspaceJobs.ts:10-47`, but loses state on restart. LitFolio persists every progress update through one SQL `UPDATE ... RETURNING` at `L:src-tauri/src/storage/jobs.rs:120-138` and has status/time indexes at `L:src-tauri/migrations/0033_jobs.sql:23-24`. | Active lookup/event fanout remains expected `O(1)`. Coalescing changes persistence from `O(P)` writes for `P` raw progress ticks to `O(T)` interval/meaningful updates, reducing WAL/fsync pressure while retaining restart truth. | Core host job runtime and event ledger; plugin-specific checkpoints/results remain plugin-owned. | Under 100 concurrent jobs emitting 20 raw ticks/s each for 60 s, persisted progress writes must stay `<= 500/s` total while terminal states are durable before acknowledgment and UI event delivery p95 stays `<= 100 ms`. |

## Priority conclusion

The first measurable wins are: indexed backlinks instead of frontend scans; linear revision-local normalization plus bounded remapping; crash-atomic file replacement combined with transactional/journaled multi-resource commits; and cancellation tokens tied to actual execution. RRF/vector reuse is valuable but remains optional `library-ask` work and must not add startup I/O to the core.
